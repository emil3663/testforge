## Decisions

1. **The display name is "Mr Onion".** (Emil, 2026-10-30; D39)
   - Written "Mr Onion", without a full stop, in UI, reports, docs and the
     README. The tagline is "Mr Onion: peel back every layer" (D39).

2. **The technical name is `mr-onion`; settings use `MRONION_`.**
   (Emil, 2026-11-08)
   - Repo `emil3663/mr-onion`; package `mr-onion`; command `mr-onion`
     (`mr-onion run`); bin file `bin/mr-onion.mjs`; image
     `ghcr.io/emil3663/mr-onion` (TFP-247); plugin `mr-onion-skills`,
     marketplace `mr-onion-skills-marketplace`; `--out` default
     `./mr-onion-out`.
   - Settings: every `TESTFORGE_X` becomes `MRONION_X`, the rest of the name
     unchanged. Code identifiers use `mrOnion` / `MrOnion` where a name is
     needed.
   - Data folder: `%LOCALAPPDATA%\MrOnion`,
     `~/Library/Application Support/MrOnion`, `$XDG_DATA_HOME/mr-onion`
     (`~/.local/share/mr-onion`).
   - Rejected: `mronion` everywhere, which gives one spelling but reads as
     "mro-nion". A hyphen is valid in every place `mr-onion` goes; it isn't
     valid in environment variable names, hence `MRONION_`.

     `GENERATOR_COMPARISON.md` and `APPLICATION_OVERVIEW.md`), `CLAUDE.md`,

     "Mr Onion".
   - Every `TESTFORGE_*` setting, including the child-process protocol

   - The plugin and marketplace names.
   - Workflow step names~~, and the nightly's secret (Decision 9)~~.

   - **[for Emil]** The generated suite's own text: the header comment, the

5. **Old names keep working until 1.0, with a deprecation notice.**
   (Emil, 2026-11-08)
   - `testforge` stays a second `bin` entry, and `npm run testforge` stays a
     script. Both print one line on stderr: "`testforge` is now `mr-onion`;
     the old name stops working at 1.0." Then they run the same CLI, with
     the same exit code.
   - Every setting is read as `MRONION_X`, then `TESTFORGE_X`. When the old
     name supplied the value, the app prints one notice per process naming
     both, on the server log or CLI stderr. When both are set and differ,
     the new one wins and the notice says so.
     **Amended 2026-11-09 (Emil, owner decision):** a blank `MRONION_X`
     (empty or only spaces) doesn't hide a `TESTFORGE_X` that has a value:
     the old value is used, and the notice says the new name is blank. A
     pipeline that templates in an empty new variable keeps its old one. A
     blank `MRONION_X` on its own stays as it was: returned blank, which
     each reader treats as unset.
   - Removal of the old command and the old user-set names is planned with
     1.0 (the versioning rule, TFP-257: 1.0 after Phase 47 declares the CLI
     and report stable). The removal needs its own ticket at that time.
   - Rejected: two minor releases (could fall before 1.0 and break pinned
     pipelines mid-0.x); a fixed date (the project versions by phase, not
     calendar).

6. **The data folder moves once.** (Emil, 2026-11-08)
   - On the first start that resolves the data folder: if the new default
     folder doesn't exist and the old default does, the old folder is
     renamed to the new one (same parent, so a rename, not a copy), and one
     notice says where it went.
   - A data folder the user set (`MRONION_DATA_DIR`, `TESTFORGE_DATA_DIR` or
     `--data-dir`) is never moved: it is used where it is.
   - **[for Emil]** When both default folders exist, the new one is used,
     nothing is merged, and the notice names the old folder as left in
     place.
   - **[for Emil]** When the rename fails (a file held open, a permission
     error), the old folder is used for that process, the notice says why,
     and the next start tries again. A run never starts with an empty
     folder because a move failed.
   - Rejected: copying (doubles the disk, and two copies drift); reading the
     old folder forever (the old name stays on disk with no end).

7. **Saved runs and baselines keep working across the rename.**
   (Emil, 2026-11-08, the planning brief)
   - A `run.json`, run folder or site suite written by 0.2.x loads, diffs
     and serves as `--baseline <id>` and `--baseline latest` unchanged.
     Nothing in their format is renamed.
   - The report footer names the product by the version that ran: a run
     stamped below 0.3.0 says "TestForge <version>", and later runs say
     "Mr Onion <version>". A report never claims a past run was made by a
     name it didn't have.

8. **Saved suites aren't rewritten; their child processes get both names.**
   **[for Emil]**
   - A reused site-suite unit or library entry keeps its text, so it may
     check `TESTFORGE_INTERACTIVE`. Every run's child environment sets each
     protocol and gate setting under both names, with the same value. An
     old saved suite therefore runs exactly as before, interactive tests
     included.
   - This child-side double setting does **not** end at 1.0 with Decision
     5's removals. It ends only when saved units carrying old names are
     regenerated or rewritten (D43). Until then, the 1.0 removal ticket
     leaves it alone.
   - Rejected: rewriting saved suites in the data folder (it changes the
     tester's files, breaks `writtenHash`'s hand-edit detection, and edits
     promotion evidence).

9. **The nightly's secret is renamed with a fallback.** **[for Emil]**
   - `nightly.yml` reads `secrets.MRONION_SMTP_PASSWORD || secrets.TESTFORGE_SMTP_PASSWORD`.
     The owner adds the new secret in GitHub's settings (an owner action,
     outside the repo), and deletes the old one after the first green
     nightly on `main` sends the email. Both steps are confirmation
     required.
   - A repo rename keeps secrets, issues, Actions history, Dependabot and
     CodeQL settings.

   **Amended 2026-11-08 (Emil):** the secret is **not** renamed in this
   phase. `TESTFORGE_SMTP_PASSWORD` is only the label GitHub stores the
   mailbox's app password under; it isn't user-facing, and the mailbox
   itself stays (Decision 4). It keeps its name until a new mailbox is
   decided (D44), so there is no fallback expression and no owner step in
   GitHub's settings. `check:old-name`'s allowlist carries it, with this
   reason. The sender display name still becomes "Mr Onion nightly".

10. **The GitHub repo is renamed at the merge, by the owner.** **[for Emil]**
    - Sequence: the branch passes Gate B; the owner renames
      `emil3663/testforge` to `emil3663/mr-onion` in GitHub's settings
      (confirmation required); Claude Code runs
      `git remote set-url origin https://github.com/emil3663/mr-onion.git`

    - The branch's links already say `emil3663/mr-onion`. They resolve from

11. **"Identical except the name" is measured, not read.** **[for Emil]**
    - `check:template-unchanged` gains `--rename-map <file>`, a committed

      (`scripts/template-unchanged/rename-map.json`). It applies the map to
      the base ref's output, then compares byte for byte with the head's.
      Exit 0 only when every fixed input is identical.

      in the ticket's evidence.
    - The map holds only name tokens (`TestForge` → `Mr Onion`,
      `TESTFORGE_` → `MRONION_`, `testforge-` → `mr-onion-`,
      `__testforge` → `__mrOnion` and so on). A token that isn't a name is
      a review finding.

## Acceptance Criteria

1. **Behaviour unchanged before any name changes (TFP-275).**
   - `check:template-unchanged` against the lock's `main`: every fixed input
     identical, with no map.
   - The unit, self-test and regression suites pass in full. No direct
     `process.env.TESTFORGE_*` read remains outside the settings module
     (a grep, quoted).

2. **Old and new settings and commands (TFP-276).**
   - Each setting works under `MRONION_X`, and under `TESTFORGE_X` alone
     with exactly one notice per process. With both set and different, the
     new value is used and the notice says so. Unit tests show each case,
     seen failing first.
   - `mr-onion run` and `testforge run` give the same exit code, JUnit and
     `report.json` (apart from run id and timings) against local Toolshop
     clean and with-bugs. `testforge` prints the deprecation line on stderr,
     and `mr-onion` prints nothing extra.
   - A run's child environment carries every protocol and gate setting
     under both names (a test records the child's environment).
   - The template check is still identical with no map (the generated text
     doesn't change in this ticket).

3. **The data folder (TFP-277), Gate A.**
   - On Windows, with only `%LOCALAPPDATA%\TestForge` present (runs, a site
     suite, a candidate): the first start renames it to `MrOnion`, prints
     the notice once, and the UI lists the same runs. `--baseline latest`
     takes the same run as on 0.2.0. A saved site suite is reused, not
     regenerated.
     **Amended 2026-11-09 (Gate A; the criterion was written from Phase
     47's context line, which the code doesn't bear out):** the default
     data folder holds site suites, candidates and gap-writer settings,
     not the UI's runs. Runs are in the repo's `runs/` (`RUNS_ROOT`)
     unless the runs folder is set inside the data folder, as `--data-dir`
     does. So the criterion reads: the UI's candidate list is unchanged,
     and a run kept in the data folder (via `--data-dir`) serves as
     `--baseline latest` after the move. The repo's `runs/` isn't touched.
   - The same on Linux (`~/.local/share/testforge` → `mr-onion`), in the
     WSL clone. macOS is covered by unit tests only, stated as a limit.
   - Both folders present: the new one is used, nothing is moved, and the
     notice names the old one. A held-open file in the old folder (Windows):
     the old folder is used, the notice gives the reason, and the next start
     moves it.
   - A user-set data folder (either setting name, or `--data-dir`) is never
     moved.
   - A 0.2.0 `run.json` diffs against a new run and serves as `--baseline`
     with the same known/new/fixed split as before the rename.

4. **The generated suite (TFP-278).**
   - `check:template-unchanged <before> <after> --rename-map …`: every fixed
