# Test cases: Test suite (TST)

Section 3.9 of the [test plan](../../TEST_PLAN.md), which keeps the app overview, the feature status, the known limitations and the index of areas. Since TFP-253 each area's cases are in a file of their own; a ticket names the area it touches.

| ID | Test | Expected Result | Status |
|----|------|-----------------|--------|
| TST-01 | Unit tests that need a real browser skip, with the reason, where Chromium isn't installed (TFP-125, Phase 36 Decision 3; `src/test-support/chromium.ts`) | Ten unit tests drive a real Chromium: six launch it directly (accessible names, the per-type check, link locators, the image-link case, database field locators, session cookies), and four route tests make the route inspect a page. Where Playwright's Chromium isn't installed they failed, for a reason that had nothing to do with the code, as the Gate C verification sandbox showed. Each now passes node:test's `skip` option the reason from `chromiumSkipReason()`: "needs a real browser, and Playwright's Chromium is not installed (expected at <path>); install it with: npx playwright install chromium". The other tests in the same files still run. **Measured, 2026-09-30:** with `PLAYWRIGHT_BROWSERS_PATH` pointed at an empty folder, `npm run test:unit` gives 340 passed, 10 skipped with the reason, 0 failed; with Chromium installed, 350 passed, 0 skipped. | ✅ |
| TST-02 | Real-browser unit tests run Playwright in a folder of their own (TFP-208; `src/test-support/playwright-cli.ts`) | Every unit test that runs a generated spec through the Playwright CLI does it through `runPlaywrightSpec`: its own folder under `.playwright-unit-runs/`, with a config that is the repo's with `testDir` set to that folder, so Playwright's start-up walk of its test folder sees no other run's files. R1's (TFP-207) `cookie-scope.test.ts:90` and an earlier `api-fields.test.ts` case failed with a report holding no test; the cause, named by the helper's first run: the repo config's `testDir` is the shared `.playwright-runs`, and a folder another run removed mid-walk failed it (`ENOENT: no such file or directory, scandir '...'`). A run whose report holds no test fails at once, naming its exit code, the report's errors and its error output (no retry). A folder Windows still holds (`EBUSY`, a failed test's video and trace) is retried and left, never failing a test; a later run removes it after an hour. | ✅ |
| TST-03 | A unit test that starts a run waits until the run is saved, not just finished (TFP-208; `src/test-support/saved-run.ts`) | `waitForSavedRun(runId, limit)` returns once the job has its result and its `run.json` is written (no `run.json.tmp` left). A job's result is set before `run.json` is written; a test that returned at the result left that write running into its file's cleanup, which removes the runs folder, and the late rename failed the file as an unhandled rejection (`ENOENT ... rename 'run.json.tmp' -> 'run.json'`, `hardening.test.ts`, once in TFP-208's first full unit run, a flake no earlier run showed). All five such waits use it: `hardening.test.ts`, `candidates.test.ts` (two), `promoted.test.ts`, `stale.test.ts`. | ✅ |
| TST-04 | CI runs the unit suite and the template check nightly and on manual dispatch, not on every push (TFP-210; `.github/workflows/nightly.yml`) | Six jobs, on a 02:00 UTC schedule and on `workflow_dispatch`: `audit` (TFP-266), `dead-code` (TFP-259: `npx knip`, `knip.jsonc`), `issue` (TFP-252, TST-07), `notify` (TFP-217, TST-06) and these two. `unit`: Node 24, Chromium installed, `npm run test:unit`, its log kept as an artifact; with Chromium there, no real-browser test skips (TST-01). `template-unchanged`: full history, `npm run check:template-unchanged -- <base> HEAD`, the base the recorded baseline (`TEMPLATE_BASELINE`, `6211ae7`) unless dispatch names another; a deliberate change of template output updates the baseline in its own commit. Neither runs on a push. The regression workflow builds once, through `test:regression:allure` (TFP-208's build first, `webServer` start only), no separate `npm run build`. **Proven (2026-10-19, `4eff1dc`, dispatched by hand; `benchmarks/2026-10-19-tfp210/`):** `unit` green: 575 tests, 574 passed, 0 failed, 1 skipped (Windows only, with its reason), suite 1,123 s, job 1,181 s. `template-unchanged` green: 166 of 166 identical against `980346f`, job 22 s. Regression green: 57 passed, built once, job 403 s. | ✅ |
| TST-05 | A real-browser case that needs a worker count sets it, so it doesn't depend on the machine (Phase 39 rulings on `70a0ad3`, ruling 1; `setMachineLimitForTests` in `src/lib/run/host-limits.ts`) | As the ownership stub does, the override stands in for the machine's limit, in tests only; nothing in the app sets it, and a capped host still gets at most 3. Set in the cases that need more than one worker: TFP-265's restart case and Acceptance Criteria 6's (3), and `split.test.ts`'s two executor cases (2). **Proven (2026-10-30, WSL, `taskset` giving Node 2, 4 and 6 cores, so a real machine limit of 1, 2 and 3):** `host-limits`, `cap-arrivals`, `cap-starved` and `split` together, 37 of 37 at each limit, 0 skipped, on the final code. On the same files before the change, at limit 1: 5 of 35 failed (the 4 worker-count cases and the waiter case below); at limit 2: 2 of 35 (the restart case, as on the nightly of 28 to 30 Oct, and the waiter case). Those limits' waiter failures (next request after 724 and 712 ms, against at least 950) went once `takeSlot` kept its fetch response: garbage collecting an unread response closes its connection, measured in a probe (3 of 3 unkept closed with no release, 0 of 3 kept). | ✅ |
| TST-06 | Every nightly says how it went, on its own page and by email (TFP-217; unit: `scripts/nightly-email/summary.test.mjs`; `.github/workflows/nightly.yml`, job `notify`) | After all four jobs and `issue` (TST-07), whatever their results, `notify` writes the summary to the run's page and sends it from `testforgeapp@gmail.com` through Gmail (port 465, TLS, the `TESTFORGE_SMTP_PASSWORD` secret, on the send step only) to the `CI_REPORT_TO` variable. Subject `TestForge nightly: PASS` or `FAIL`, the short commit and the date; FAIL when any job didn't succeed or didn't report. Plain-text body: the run's link, trigger, commit, template base; `unit`'s result, counts and failing tests (at most 20, then "and N more"); the template check's line; `audit` and `dead-code`. Counts that can't be read are said to be, never left out. A failed send fails the job. **Proven (equivalence partitioning, boundary at 20 names; each assertion seen failing by mutant, 15 of 15):** PASS; FAIL for each of the four jobs failed, cancelled or skipped, and for a job not reported; 20 and 23 failing tests; a cancelled job with no counts; a green job whose counts weren't found; the log's parser on node:test's output, colour codes included; a send with no password or recipient fails before connecting; a refused send fails with the server's reason and without the password; a rejected recipient fails. Live (2026-11-02, nightly 41514922513, `benchmarks/2026-11-02-tfp217-email/`): sent, Gmail `250 2.0.0 OK`, the password only as `***` in the log; the owner received it at 22:17 with the body as on the run page, and its link opened the run. A FAIL email and a cancelled run are left to the first real ones (owner, 2026-11-02). | ✅ |
| TST-07 | A red nightly opens or updates one failure issue, and the next green one closes it (TFP-252; unit: `scripts/nightly-email/issue.test.mjs`; `.github/workflows/nightly.yml`, job `issue`) | After the four check jobs, whatever their results unless the run was cancelled (then it is skipped, and the email says so), `issue` (its own job, with `issues: write` and `actions: read`; never the SMTP password) runs `notify.mjs issue`, no model. A red night (the email's verdict, `nightlyPassed`) with no open issue titled `Nightly failing` opens one; with one open, comments on it; a green night closes it with a comment naming the run; a quiet green night only reads. The report: the run's link, the short commit, each job's result, the failing tests (as the email names them) and the commits since the last run of `nightly.yml` that concluded green on the branch, with GitHub's compare link (at most 20 listed, then "and N more" from GitHub's total); no green run, a green run that can't be looked up, or a range that can't be listed, is said with `gh`'s own reason, and the issue is opened all the same. "Green" is the run's own conclusion, which counts `issue` and `notify` too, so a range can be longer than it need be, never shorter. Test names and commit subjects are in a text fence longer than any run of `~` inside it, so an `@name` in one notifies nobody. A branch's runs use `Nightly failing on <branch>`, so a test dispatch can't touch main's. The open issue is found by exact title through the list API, not search, so one opened a minute earlier is found. The email links the issue (opened, updated, closed), or says the issue job couldn't do its part. **Proven (unit, offline; `gh` played by `fake-gh.mjs`, a JSON state, not GitHub):** the plan's four cases; red, red, green, green through `notify.mjs`: one issue opened, then commented on, then closed, then left alone, an issue with another title untouched; a branch's red night opens its own issue and leaves main's; a failed green-run lookup still opens the issue; a `~~~~` name, 300 commits, gh's 404 and 502 reasons; the email's line for each action and for an issue job that failed or was cancelled. Against `HEAD`'s `notify.mjs` the command tests fail (`unknown command: issue`); with the email's line removed, its two tests fail; each review fix undone (a fixed fence, the listed count, stderr not captured, a lookup that throws) fails its test. **Proven live (2026-11-04, branch `tfp-252-check`, four manual dispatches, branch deleted after):** run 41741173103 green, issue job `none`, no email line; an empty commit, then run 41743846846 with `template-base=435d78f` (template check 170 of 172, so red) opened #17 "Nightly failing on tfp-252-check" with the run, each job's result and the 1-commit range from the green run's `bc54e7d`, email "Failure issue: opened …/issues/17"; run 41746797189, the same, commented on #17 and opened none, "updated"; run 41749704644 green closed #17 with "Green again: …", "closed". One issue opened in all, closed at the end; none for `main`. Email lines read from bodies rebuilt from each notify job's logged inputs; each sent subject matched the log. **Not proven:** the cancelled-run skip (workflow only). **Gap seen live, closed (Emil, 2026-11-04):** a failure outside the unit job was named by its result alone. A red template check now carries its own line (`**Template check:** N inputs, N identical, N different`, or that it can't be read), as the email does; `audit` and `dead-code` have no line of their own. Unit-proven (fails without the change: 2 tests), not re-run live. | ✅ |
