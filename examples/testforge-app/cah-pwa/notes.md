# TFP-074: TestForge's app, run end-to-end against cah-pwa

Real crawl → introspect → generate → run pipeline output, target `cah-pwa`
served locally at `http://localhost:8001` (its own `GETTING_STARTED.md` says
port 8000; that port was already held by an unrelated local project on this
machine, so 8001 was used instead — incidental to the ticket, not a
deviation from the target). Warts recorded, not cleaned up before showing.

## Method — same real deviation as TFP-040, restated

No browser-automation tool is available in this session, same gap TFP-036's
spike found and TFP-040 documented. As with TFP-040, this run drove
TestForge's own API routes directly (`/api/crawl`, `/api/introspect`,
`/api/generate`, `/api/run`), in the same sequence and payload shapes the
React UI itself uses (`contentProfile` passed to `/api/generate` is the raw,
unmodified response of `/api/introspect`). Every route runs its own real
headless Chromium server-side. The one thing this doesn't prove is that the
UI's button-click handlers assemble these same payloads.

## Which generator ran

**The template-based fallback generator, again.** `.env.development` has
`OPENAI_API_KEY=` (empty), unchanged from TFP-040's environment. Confirmed
in the generated file's own header: `// Generated by TestForge without an
OpenAI API key.` Same generator, second target — a genuinely comparable
data point with TFP-040, not a confound.

## The reachability question — answered as a specific fact, not assumed

**TestForge's unauthenticated crawl reaches exactly one page (`/`), and
never gets anywhere near the auth wall, let alone past it — because there
is nothing past `/` for a same-origin BFS crawler to walk into.**

Read directly from `src/app/api/crawl/route.ts` before running anything:
the crawler's only mechanism for discovering new pages is
`document.querySelectorAll("a[href]")` on each visited page, filtered to
same-origin (`route.ts:139-153, 208-236`). `cah-pwa` is a single-page app —
`index.html` has exactly one `<a href>` in the whole document (an external
link to the `json-against-humanity` GitHub repo, `target="_blank"`, so
even same-origin-only filtering would reject it). Every other screen
(sign-in, create room, join room, friends, admin) is a `<div>`/`<button>`
that `app.js`'s `showScreen()` toggles via CSS, not a navigated URL. There
is no room-creation screen, or any other screen, for the crawler to "stop
at" — the crawl completed in one hop with `pageCount: 1`, identical in
shape to TFP-040's `test-assist` result (also exactly 1 page, also an SPA
with no internal `<a href>`s).

**This is a different, more useful fact than "reachability is blocked by
Firebase auth."** The auth wall is real (confirmed below), but it's not
what stops the crawl — the crawl never gets far enough to *hit* the auth
wall in the first place, because BFS-over-`<a>` has nothing to traverse on
an SPA regardless of what's behind the login form. Anything past `/` would
need a crawler that clicks buttons and drives view transitions, which is
categorically different from what TestForge's `/api/crawl` does today —
this is exactly the authenticated/interactive-crawl gap the decision doc
calls out as a separate, already-tracked roadmap item, not something to
pull into this ticket.

**Aside also confirmed while investigating this, since it changes how the
result should be read:** `cah-pwa` has a client-side auth bypass active
specifically on private-network hosts (`app.js`'s `isPrivateNetworkHost` /
`canUseAdminLogin` / `canUseRegressionLogin`, `app.js:140-168`) — signing in
with a known local regression-test credential pair skips
`firebaseAuth.signInWithEmailAndPassword` entirely and logs in a synthetic
local session. Serving on `localhost:8001` qualifies. **This bypass is
irrelevant to what TestForge's crawl reaches**, because the crawl never
submits the sign-in form — it only follows `<a href>` links, and the
sign-in form isn't one. It would matter to a *future*, form-filling crawl
mode; noted here so that future work doesn't have to rediscover it.

## Step 1 — Crawl

`POST /api/crawl {"baseUrl":"http://localhost:8001"}`, polled to completion
(5.04s).

**Result: exactly 1 page (`/`), title "Cards Against Humanity".** See above
for why — a real, checkable fact about the target's markup, not a limit of
this run.

## Step 2 — Introspect

`POST /api/introspect {"baseUrl":"http://localhost:8001","paths":["/"]}`.

Found 8 headings, 8 top-level buttons, 1 external link, and **38 actionable
elements total** — including inputs and buttons that belong to screens a
signed-out, unauthenticated visitor never sees (`roomName`, `joinCode`,
the `gameMode` radios, `btnCreateRoom`, `btnJoin`, `friendName`,
`customDeckCards`, etc.), each correctly flagged `"isVisible": false`.

**This is worth stating precisely, because it looks like it contradicts the
crawl result above and doesn't:** introspection isn't crawling to new URLs
— it's a static DOM scan of the *one* page the crawler reached. Every
screen in `cah-pwa` (menu, create-room, join-room, friends, admin, deck
checkout) is markup that already exists in `index.html` at load time,
hidden with CSS/`hidden` attributes until `app.js` toggles it. So a single
DOM scan of `/` sees all of it, in the same sense TFP-040 found `test-assist`
had "28 actionable elements" behind conditional visibility on its one page.
The difference here is scale and stakes: several of these hidden elements
belong to Firebase-gated *gameplay* screens, not just alternate tool modes.

## Step 4 — Run

`POST /api/run` with the generated code, same practices, `baseUrl:
"http://localhost:8001"`. Polled to completion (~100s wall time).

**Real result: 108 tests, 97 passed, 11 failed. `runStatus: "failed"`.**
Full structured report saved as `run-report.json`.

### The 11 failures, all real, all understood

**6 share one root cause, but it's a different failure signature than
TFP-040 saw, worth naming precisely:** `TFFU-030/031/032` and
`TFAC-030/031/032` all target the same three `gameMode` radio inputs
(`Classic`/`Wild 🔥`/`Question First ❓`, `index.html:159-161`) via
`page.getByRole('radio', { name: ... })`, and all fail with **`element(s)
not found` / `expect(locator).toBeAttached() failed`** — not
`toBeVisible()` returning `hidden`, the failure mode every one of TFP-040's
7 false positives shared. The reason: these radios sit inside a
`display:none`-hidden container (the create-room panel, only shown after
`showScreen('createRoom')`), and `getByRole()` resolves through
Playwright's accessibility-tree snapshot, which excludes `display:none`
subtrees entirely — unlike a plain CSS locator combined with
`toBeVisible()`, which still finds the element and reports it as hidden.
Same underlying cause as TFP-040 (a conditionally-visible element the
generator can't distinguish from a permanently-visible one), a different
symptom because this generator run happened to reach for `getByRole()`
locators on these elements instead of ID/CSS locators. **3 more
(`TFUS-009/010/011`)** are the same three radios again, checked under
`Usability Coverage`'s "non-generic guidance text" test, which don't fail
fast — they burn the full 30s test timeout waiting for state that never
arrives, rather than failing on an immediate "not found."

**1 (`TFFU-048`) is the same specific, real, low-stakes finding TFP-040
already surfaced on a different target** — `expect(received).toBeTruthy()`
on "does the stylesheet define `:visited` link styling," received `false`.
Confirmed directly: `style.css` has no `:visited` rule anywhere. Genuinely
low-value for a page with exactly one external link (same judgment TFP-040
reached for `test-assist`), but worth flagging here specifically because
it's now a **repeat finding across two unrelated targets** from the same
generator check — a pattern, not a one-off.

**1 (`TFAC-042`) is a real generator misclassification, not a `cah-pwa`
defect — the most interesting single finding of this run.** The failure
reads: *"🏠 Create Room is part of a detected toggle/selection group but
exposes no ARIA state attribute... so assistive technology has no way to
tell which member is current."* The generator grouped the six top-level
menu buttons (`btnCreateRoom`, `btnJoinRoom`, `btnFriends`, `btnStats`,
`btnDecks`, `btnAdmin`) under one `groupId: "group-1"` in introspection
(confirmed in the introspect response) and its accessibility check assumed
any grouped set of buttons is a *toggle group* — mutually-exclusive
selection state, like a tab strip or segmented control, which does need
`aria-pressed`/`aria-selected`. **These six buttons are not that.** Each
one is a plain navigation entry to a different screen
(`index.html:45-69`, `class="menu-card"`) — clicking `Create Room`
navigates away, it doesn't toggle a shared selected state among the six.
None of them has, or should have, `aria-pressed`. The generator's grouping
heuristic (proximity/shared container) over-fired here: it's a real,
specific, checkable false positive, distinct in kind from every other
failure in this run.

## What worked

- The pipeline ran end-to-end for real, same method as TFP-040, this time
  against a target with actual external service dependencies (Firebase,
  Gemini) rather than a fully self-contained tool.
- 97 of 108 tests are genuinely correct, including on a page with far more
  DOM surface (38 actionable elements across 6+ conceptual screens) than
  `test-assist` had (28, across effectively 1 screen).
- The reachability boundary is now a stated, checkable fact instead of an
  assumption either way: crawl reaches 1 page because the app has 0
  internal `<a href>` links, full stop — not because of Firebase, not
  because of an auth redirect. The auth wall is real but structurally
  irrelevant to *this* crawler.

## What didn't

- The same systematic blind spot TFP-040 found (conditionally-visible
  elements treated as unconditionally visible) reappears here, but through
  a second locator strategy (`getByRole`, accessibility-tree-based) that
  fails with a different signature (`not found`/timeout) than the first
  (`toBeVisible` → `hidden`). Anyone triaging these failures needs to know
  both signatures point at the same root cause, or risks writing two
  separate bug reports for one generator limitation.
- The grouping heuristic behind `TFAC-042` treats "buttons that share a
  container" as "buttons that share toggle state" — true for some UIs,
  false for a plain navigation menu, and `cah-pwa`'s main menu is the
  latter. This is a new failure mode TFP-040 didn't surface (`test-assist`
  had no comparable button group to misclassify).
- Nothing here exercises real gameplay, sign-in, or Gemini-backed behaviour
  — confirmed above as a structural fact about the crawler, not a gap in
  this run's execution.
