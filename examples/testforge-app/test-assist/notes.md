# TFP-040: TestForge's app, run end-to-end against test-assist

Real crawl → introspect → generate → run pipeline output, target
`test-assist`'s browser build served locally at `http://localhost:4321`.
Warts recorded, not cleaned up before showing.

## Method — a real deviation, stated up front

No browser-automation tool (Playwright MCP or otherwise) is available in
this session — the same gap TFP-036's spike found and documented. The
ticket asked for this to run "through TestForge's actual UI or API, not a
script that bypasses it." Without a browser tool, driving the rendered UI
by clicking isn't possible; what *is* possible, and what this run actually
did, is call TestForge's own API routes directly, in the exact sequence and
with the exact payload shapes its own UI uses — confirmed by reading
`src/app/_hooks/useGeneration.ts` (the `contentProfile` passed to
`/api/generate` is the raw, unmodified response of `/api/introspect`, not
a script-side reinterpretation of it) before making a single call. Every
API route exercised (`/api/crawl`, `/api/introspect`, `/api/generate`,
`/api/run`) runs its own real headless Chromium via Playwright server-side,
same as it would from a click. The one thing this doesn't prove is that the
React UI's own button-click handlers correctly assemble these same
payloads — everything downstream of that assembly is real.

## Which generator ran

**The template-based fallback generator, not OpenAI.** `.env.development`
has `OPENAI_API_KEY=` (empty) and this wasn't overridden. Confirmed
directly in the generated file's own header comment: `// Generated by
TestForge without an OpenAI API key.` This matters for reading the results
below: the suite's shape (heavy per-element enumeration, generic
category-level tests) is what the template generator produces, not a
judgment call an LLM made about this specific app.

## Step 1 — Crawl

`POST /api/crawl {"baseUrl":"http://localhost:4321"}`, polled to
completion (1.78s).

**Result: exactly 1 page (`/`).** Not a bug - `test-assist`'s browser build
is a single-page canvas tool; its only two `<a>` tags are external links to
GitHub (`← Repo`, `Also ships as a desktop app →`), so a same-origin
crawler correctly finds nothing to walk into. Worth noting since it means
`crawl-and-classify-pages` (the newest skill, not yet run live per its own
stated caveat) wouldn't have much more to classify here either - this
target is a poor fit for testing crawl breadth, a real fact about the
target, not the tooling.

## Step 2 — Introspect

`POST /api/introspect {"baseUrl":"http://localhost:4321","paths":["/"]}`.

Correctly extracted: 2 headings (`Quick Capture`, `Tools`), 28 actionable
elements (every tool button, both mode tabs, sliders, undo/redo/clear,
both export buttons, the hidden file input, the hidden recording/text-popup
controls - all discovered regardless of their current CSS visibility,
which becomes the root cause of the failures below), and the 2 external
links, each correctly classified as `external`.

## Step 3 — Generate

`POST /api/generate` with the introspect response as `contentProfile`,
`selectedPractices: [functional, responsive/mobile, accessibility,
usability]`, description: *"Test the Test Assist screen capture and
annotation tool. A user can capture a screenshot or upload an image, then
use annotation tools (select, highlight, text, circle, arrow, rectangle,
pen) to mark it up, undo and redo changes, and export the annotated image
as a PNG or export the raw annotations as JSON. The page should also work
well on mobile."*

**42 tests generated** (`generated.spec.ts`, saved as-is): 39 under
`Functional Coverage` (`TFFU-001`–`TFFU-039`, one test per discovered
interactive element plus 11 link-health checks), 1 under `Usability
Coverage`, 1 under `Responsive Coverage`, 1 under `Accessibility Coverage`.
The lopsidedness is real, not a sampling artifact - see the comparison note
for what this means.

## Step 4 — Run

`POST /api/run` with the generated code, same practices, `baseUrl:
"http://localhost:4321"`. Polled to completion.

**Real result: 42 tests, 34 passed, 8 failed. `runStatus: "failed"`.**
Full structured report saved as `run-report.json` (the actual seven-tab
payload: summary, execution, defects, coverage, performance, usability,
seo).

### The 8 failures, all real, all understood - not "8 failures occurred"

**7 of the 8 share one root cause**, confirmed from each failure's own
error message, not inferred: every one is `expect(locator).toBeVisible()`
failing with `Received: hidden` against an element that is *correctly*
hidden by the app's own design until a prerequisite user action happens -
`#btnRecord` (hidden until Video mode is selected), `#btnClearSession`
(hidden until a session has actually been restored), `#uploadImage` (a
file input deliberately styled invisible, with a visible label wrapping
it - a common, valid pattern), `#btnStopRecord` (inside the recording
badge, hidden until recording starts), and `#textInput`/`#btnTextOk`/
`#btnTextCancel` (inside the text popup, hidden until the Text tool is
active and the canvas is clicked). The generator's introspection correctly
found all of these elements exist; it has no way to know any of them are
*conditionally* visible, so every "action/form element check" test
defaults to asserting unconditional visibility. These are false positives
in the generated suite, not defects in `test-assist`.

**The 8th (`TFFU-036`) is different and less clear-cut**: `expect(received)
.toBeTruthy()` on a check for whether the stylesheet defines `:visited`
link styling, received `false`. `test-assist`'s `style.css` doesn't appear
to define one. Whether that's worth fixing is genuinely unclear for a tool
with exactly two, both-external links - noted as a real finding, not
dismissed as another false positive, since it wasn't traced to a "the
generator asserted the wrong thing" root cause the way the other 7 were.

## What worked

- The pipeline ran end-to-end for real, with no manual intervention beyond
  driving the API calls: crawl → introspect → generate → run, each step's
  real output feeding the next exactly as the UI would.
- The generated suite is syntactically valid, idiomatic Playwright, and 34
  of 42 tests are genuinely correct.
- The structured report correctly classified all 8 failures as `Critical`/
  `Major` defects with full artifacts (screenshot, video, trace, error
  context) per failure - the reporting machinery itself has no gaps here.

## What didn't

- The template generator has a systematic blind spot: it cannot tell a
  conditionally-visible element from a permanently-visible one, and
  defaults to asserting the stronger claim. On an app with several
  legitimately-hidden controls (a common, valid UI pattern - modals,
  file-input replacements, mode-gated buttons), this produces a
  predictable band of false positives, not occasional noise.
- Coverage is breadth-first and shallow: 39 of 42 tests are "does this
  element exist and is it visible," not "does clicking it do the right
  thing." Nothing here verifies an annotation actually gets drawn, that
  undo actually removes it, or that export actually produces a file with
  the right content - see the comparison note for how this contrasts with
  the other two suites.
