# TestForge — Test Plan

**Version:** 1.0
**Last updated:** 2026-09-17
**Status:** In active development

## 1. App Overview

TestForge is an AI-native test automation assistant: a tester describes what
to check in plain English (or picks from best-practice coverage areas), and
TestForge crawls the target site, inspects what's actually on each page, and
generates a deterministic (or, with an OpenAI key configured, AI-assisted)
Playwright TypeScript suite from that inspection. The generated suite runs
through an async lifecycle with live progress, and results land in a
seven-tab structured report with HTML export. Main areas: suite creation,
crawl, introspect, generate, run, report, export, and save-suite.

## 4. Known Limitations & Gaps

1. **`/api/run`'s execution model is unsandboxed, in-process code execution.** It runs caller-supplied Playwright code with the privileges of the user running the dev server — no authentication, no sandboxing, no multi-tenant isolation. This is documented, intended behavior under TestForge's local-only posture (see `README.md`'s Security Model), not a defect, and it is why TestForge must never be bound to a non-loopback interface or exposed through a tunnel.
2. **Chromium only.** Cross-browser execution (Firefox, WebKit) is out of scope as of Phase 16 (TFP-012); `playwright.config.ts` declares a single `chromium` project.
3. **Run persistence and diffing (Phase 17) have landed** — a finished run's config, suite, result, and evidence survive a server restart (`runs/<runId>/`, RUN-08/RUN-09), and two persisted runs of the same `baseUrl` can be diffed via `GET /api/runs/diff` for specific test-status changes, per-area coverage deltas, and newly discovered/missing elements (RUN-12). Data + API only, per the decision record's own scope lock — no diff UI yet.
4. **Coverage is now computed against the discovered surface for functional and accessibility (Phase 17 Groups 2/3, RUN-10/RUN-11)** — an element counts as covered only if it was actually the subject of an executed test, and every unmatched element is bucketed as not-selected / excluded-by-generator / generator-gap. Reliability dependency/storage surfaces and, since TFP-091, selected journeys are tracked the same way (journeys add an `interactive-skipped` bucket). Areas without a one-test-per-element generator shape (performance, security, SEO, responsive, cookie/session, database, and usability's bundled checks) still use the prior test-pass-rate rollup — there's no discovered-element surface to honestly denominate against for those.
5. **The OpenAI-backed generation path is hardened but not evaluated, and no live completion has succeeded yet.** TFP-083 (Phase 28) makes the route fail safe: a rejected call, a timeout (30s, one budget for catalog lookup plus completion), an empty completion, or no candidate model in the live catalog each return the template generator's output labelled `generatedBy: "fallback"` with a `fallbackReason`, proven by tests against a fake OpenAI server. The same fallback was also observed against the real API on 2026-09-24 (a 429 "no credits" refusal returned the labelled template, not a 500). Still open: (a) `npm run check:openai-models` confirmed all three `OPENAI_MODEL_CANDIDATES` are in the live catalog (the route picks `gpt-4.1-mini`), but its test completion was refused because the account had no API credits — re-run it once the account is funded; (b) the AI path has not been compared against the deterministic generator, and no CI job calls OpenAI with a real key (Phase 21, TFP-098/099). Hardening is not evaluation.
6. **No deployed or hosted version exists, and none is assumed.** TestForge is local-only by design; `docs/decisions/saas-prerequisites.md` records what a hosted version would actually require and states plainly that none of it is implemented.
7. **`src/lib/introspect/dom-snapshot.ts` is deliberately long (800+ lines) and exempted from this repo's 500-line max-lines lint rule.** `captureDomSnapshot` is passed by reference to Playwright's `page.evaluate()`, which serializes the function's own source and runs it inside the browser's isolated JS context — every helper it uses must stay nested inside its body, since no module system is available there. Splitting it into separate files would silently break real page introspection.
8. **Only a single-page login form is supported for authenticated runs (Phase 20, TFP-092).** They are configured in the app's "Authenticated Run" section (TFP-097) or as the `/api/run` request's `login` field. The login block is `loginUrl`, three selectors, two credential environment-variable *names*, and a post-login path/selector; multi-step logins, MFA, and CAPTCHA are not driven (the roadmap keeps login config-driven, not discovered). The login runs in the same browser context the tests do (`src/lib/run/browser-context.ts`), because a site can bind a session to the client that logged in; a target that binds to something else the context doesn't control would still refuse the session. Traces are now scrubbed of the run's credentials and session (TFP-094, RUN-18), but screenshots and videos are binary and cannot be text-scrubbed — they are kept as captured, and show whatever the authenticated page showed; trace scrubbing uses the zip reader/writer bundled inside `playwright-core` (an internal export, not a public API), so a Playwright update that moves it fails the RUN-18 regression test rather than leaking silently. **Credentials come from process environment variables only — no secret-store integration is supported (Decision 3, deferred deliberately, not silently).** The two variables must be set for the TestForge server process (a local `.env`, or the shell that starts it); a name must be upper case (letters, digits, underscore). A password that is itself all upper-case letters, digits and underscores, pasted where a name belongs, would still pass the name check and be echoed in a "variable X is not set" error to the caller (a local-only tool, and only if that variable is unset) — the check narrows the mistake, it cannot rule it out.
9. **The local (Ollama) model's suites compile, but only the type check stands between it and invented APIs, and "compiles" is not "correct".** Phase 31 update: a local-only rules layer (TFP-106, GEN-27) fixed the accessibility defect described below. Three consecutive live accessibility requests now return real checks. The history below explains why the type check exists. TFP-103 (Phase 30) adds the path (`TESTFORGE_OLLAMA_MODEL`, setup in `docs/LOCAL_MODEL_SETUP.md`). It degrades safely: unreachable, model missing, Ollama error, timeout (180s) and empty output each return the labelled template suite, proven against a fake server (GEN-22 to GEN-25). Every local suite is also type-checked against `@playwright/test` before it is labelled model output (GEN-26), because `testforge-qwen7b` invents Playwright APIs. All three accessibility-worded requests run live on 2026-09-24 produced `expect(locator).toBeAccessible()`, which Playwright does not have. The first two predate the check. The third was caught and returned as `fallbackReason: "invalid_output"`. A functional request in the same session passed and was returned as model output (GEN-21). So a broken suite is never passed off as model output, but for accessibility coverage the local path currently yields the template. What the check does not judge: whether a valid suite's assumptions are right (the passing suite guessed a `/dashboard` URL after sign-in). Three samples are not a measured rate. Still true after Phase 31: the type check cannot see a missing `await`, a wrong URL, or an assertion that doesn't pass on the real page. The Phase 31 baseline (GEN-28) found all 10 areas compile, but performance, SEO and database suites contained nothing specific to their area, security and reliability only partly, and 9 of 10 suites navigated to `/login`, copied from the rules example (confirmed and removed in GEN-30). Phase 32 also found the model reuses an example's test names and structure (GEN-30), and that one baseline suite had an unawaited, never-run assertion (GEN-29). Phase 33: a suite with a never-run assertion is now rejected (GEN-31, `unawaited_assertion`). Worked-example guides now exist for reliability, performance, SEO, database and security, sent only for the areas in scope. Live, 3 consecutive each: performance, SEO, database and security now produce category-specific checks (GEN-33 to GEN-36). Reliability now simulates real failures but often maps the request's inputs and button onto duplicate, mislabelled tests (GEN-32, ⚠️). Accessibility (GEN-27 wording, 3/3) and functional (GEN-21) did not regress. Out of scope: trying other local models, and comparing the local path against the template and OpenAI paths (Phase 21, TFP-099).

## 6. GitHub Project Board Structure

TestForge currently tracks phase work as numbered `TFP-NNN` tickets inside
`docs/decisions/phase-N-*-backlog.md`, not as live GitHub Issues. The
structure below is the suggested shape if/when this repo's tracking moves
to a GitHub Project board, kept consistent with the labels already used
across the backlog docs.

| Column | Description |
|--------|-------------|
| 🧊 Backlog | Roadmapped, not yet locked (e.g. Phase 18–21 items) |
| 🔍 Needs Investigation | Spikes / trials before a ticket is written (e.g. TFP-036's style) |
| 🚧 In Progress | Actively being worked on |
| 👀 In Review | PR open, awaiting review |
| ✅ Done | Merged |
